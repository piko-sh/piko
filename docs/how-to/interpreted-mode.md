# How to run interpreted mode

Use interpreted mode (`dev-i`) to reload `.pk` edits without rebuilding the server binary. Start with an existing Piko project and the [Piko CLI](../get-started/install.md). For the trade-offs between run modes, see [about interpreted mode](../explanation/about-interpreted-mode.md).

## Register the interpreter

In `cmd/main/main.go`, import the provider package and register it on your server before the existing `ssr.Run(...)` call. Projects created with the wizard's interpreted-mode option already include this registration.

```go
import "piko.sh/piko/wdk/interp/interp_provider_pipit"

// After ssr := piko.New(...).
ssr.WithInterpreterProvider(interp_provider_pipit.NewProvider())
```

Keep your existing bootstrap options and run-mode selection.

## Start the server

From the project root, run the following command.

```bash
piko dev-i
```

Open the address printed by the server. Edit some visible text in a `.pk` page and save it. The page should show the change after reloading, without a server restart.

## Add native package symbols

Pipit provides standard-library symbols, and Piko supplies its runtime symbols. Piko can also compile local project packages from source. Use symbol extraction for third-party Go packages, or to run a project package as native code.

Check which imports need symbol tables.

```bash
piko extract discover
```

The scan follows your project's own packages, because dev-i compiles them from source, and reports the third-party packages they import. It chooses their files as the interpreter does, with the `interp` build tag set and cgo off, so a file guarded by `//go:build !interp` does not count. Packages the server already provides, and packages named with `--ignore`, are not followed. Action packages are found through the `.pk` files that import them. Imports it cannot load are printed as warnings. To register a project package as native code instead, pass `--include-project`, which lists the project packages your `.pk` files import without following them.

If the scan finds packages and you do not yet have `piko-symbols.yaml`, create it. Review the package list before generating the tables.

```bash
piko extract init
```

Skip extraction if the scan finds no packages. `init` can create an empty manifest, but `generate` requires at least one package. If a manifest already exists, update its package list to include the imports you need.

Generate the tables from the non-empty manifest.

```bash
piko extract generate
```

Import the generated package in `cmd/main/main.go`, replacing `example.com/myapp` with your module path. Add the registration before `ssr.Run(...)`.

```go
import "example.com/myapp/internal/piko_symbols"

ssr.WithSymbols(piko_symbols.Symbols)
```

Restart `piko dev-i` to build the native symbols into the server. Regenerate the tables when exported symbols change. Restart after changing any package listed in the manifest, because its native code comes from the server binary.

## Embed files in packages dev-i compiles

Pipit cannot compile `//go:embed`. When a project package that dev-i compiles from source embeds files, move the embedding variable into a file guarded by `//go:build !interp`. Then declare the same variable in a `//go:build interp` file that reads the files at run time. Pipit sets the `interp` build tag, so the compiled binary keeps the embedded copy and dev-i reads from disk.

```go
//go:build !interp

package content

import (
    "embed"
    "io/fs"
)

//go:embed files
var embedded embed.FS

var Files fs.FS = embedded
```

```go
//go:build interp

package content

import (
    "io/fs"
    "os"
)

// dev-i runs from the project root, so the path is relative to it.
var Files fs.FS = os.DirFS("internal/content")
```

Both files must declare the same names with the same types, because the generator type-checks the `!interp` file and dev-i compiles the `interp` one. If dev-i reports a `//go:embed` problem, its error names the package and every directive, and notes that relative paths are read from the project root.

## Share state between main and pages

Dev-i runs its own copy of each project package it compiles from source, separate from the copy in the server binary, so a package variable that `cmd/main` sets is not visible to pages (see [package state](../explanation/about-interpreted-mode.md#package-state-in-dev-i)). Piko warns at start-up about the packages this affects. Decide per request instead:

```go
func Render(r *piko.RequestData, props piko.NoProps) (Response, piko.Metadata, error) {
    posts := publishing.Posts(piko.IsDevelopmentMode(r))
    // ...
}
```

Or run the package as native code by adding it to the symbol manifest with `piko extract --include-project`, then restart after each change to it.

## Read compilation errors

When dev-i cannot compile the project, it reports every problem it found in one error instead of stopping at the first. Each problem is numbered, labelled (for example `type error` or `//go:embed in a package dev-i compiles from source`), and followed by a hint for fixing it. Some problems also carry a note about what is different in a Piko project, such as where the symbol manifest lives.

## Inspect generated bytecode

To investigate a compilation problem, enable bytecode emission when registering the provider.

```go
ssr.WithInterpreterProvider(interp_provider_pipit.NewProvider(
    interp_provider_pipit.WithBytecodeEmission(".piko/bytecode"),
))
```

Restart `piko dev-i` and reproduce the problem. Find the emitted `.bin` file under `.piko/bytecode/compiled/`, then pass its path to the inspector.

```bash
piko inspect bytecode .piko/bytecode/compiled/bytecode-abc.bin
```

Replace `bytecode-abc.bin` with the emitted filename. A successful compilation also produces a `.pkasm` disassembly. For a failed compilation, read the `.error.txt` file instead. See the [interpreter API reference](../reference/interpreter-api.md#bytecode-emission) for the output files.
